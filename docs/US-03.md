## Design mapping

- User.email remains the single contact/sign-in email. Donor.phone remains the
  phone field. No new model, table, or migration is required.
- Request layer: `donors/views.py`, `permissions.py`, `serializers.py`.
- Donor & Donation Management rules: `donors/services.py`.
- Data Access: `donors/repository.py`, using the existing Django models.
- Identity comes from the authenticated request, never from writable payload fields.
- Both database writes occur in one transaction, with account/profile row locks on
  PostgreSQL. The database's case-insensitive email constraint handles collisions.
- Design changes: None for the component/entity design. This document supplies
  concrete routes and response fields for the module interface in Sprint 2.
- Python 3.12 matches the project's CI. SQLite is the existing local fallback;
  PostgreSQL remains the CI/production database.

## API contract

Send `Authorization: Bearer <access token>` obtained from registration or sign-in.

| Method | URL | Behavior |
| --- | --- | --- |
| GET | `/api/donors/me/contact/` | Get the signed-in donor's email and phone |
| PATCH | `/api/donors/me/contact/` | Update one or both contact fields |
| GET / PATCH | `/api/donors/<donor_id>/contact/` | Same, but requires the caller's own Donor ID |

`donor_id` is the Donor profile primary key, not User.id. Prefer `/me/contact/` in
the frontend. The explicit-ID route makes ownership enforcement directly testable.

Successful GET and PATCH responses (HTTP 200):

```json
{"donor_id": 1, "email": "demo.contact@example.com", "phone": "2125550100"}
```

Example PATCH:

```json
{"email": "demo.updated@example.com", "phone": "0123456789"}
```

Email must be valid and no longer than 254 characters; it is trimmed and stored
in lower case, as in US-01. Phone must be exactly 10 digits (0-9), with no spaces,
punctuation, or newline. Leading zeros are preserved. Omitted fields stay unchanged.
Empty/null values, an empty update, non-object input, and fields other than email
and phone are rejected. Password, role, account status, blood type, and ownership
cannot be modified here.

The email changes future sign-ins. Existing JWTs continue to identify the same
User ID; the password is unchanged.

| Status | Meaning |
| --- | --- |
| 400 | Invalid email/phone, empty update, or unsupported field |
| 401 | Missing/invalid token or deactivated account |
| 403 | Another donor's ID, coordinator access, withdrawn/deleted donor profile |
| 404 | Signed-in donor has no Donor profile |
| 409 | Email already belongs to another account (case-insensitive) |
| 405 | Unsupported method, such as DELETE |

Validation errors name the offending fields. Permission errors disclose no other
donor contact data. Non-owned IDs return 403 regardless of whether the ID exists.
Invalid input, duplicates, and database write failures leave both fields unchanged.

## Run and test (Windows PowerShell)

Use Python 3.12 to create a virtual environment, then install the repository's
dependencies. With `.venv` already created, activation is optional:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py test
.\.venv\Scripts\python.exe manage.py test donors.test_contact --verbosity 2
```

Tests create a separate temporary test database. No real donor data is used.

| Acceptance criterion | Tests in `donors/test_contact.py` |
| --- | --- |
| AC1: view current contact | `test_get_current_contact`, `test_get_own_contact_by_donor_id` |
| AC2: reject invalid email | `test_invalid_emails_rejected_without_saving` |
| AC3: reject invalid phone | `test_invalid_phones_rejected_without_saving` |
| AC4: save and display changes | `test_update_both_fields_and_read_again`, phone-only/email-only tests |
| AC5: no access to another donor | `test_other_donor_get_and_patch_return_403_without_disclosure` |

Additional tests cover real JWT authentication, deactivated/withdrawn accounts,
coordinator access, email duplicates, database collision/rollback, forbidden fields,
and the US-01 registration -> US-03 GET -> PATCH -> GET integration flow.

## Backend demo script

Once the dependency is available on the working branch, initialize the local
database and start the development server:

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py runserver
```

In a second PowerShell terminal, create a synthetic donor. On a reused database,
choose a fresh demo email or use the existing demo account's credentials to sign in.
The sample password is for local synthetic demo accounts only.

```powershell
$api = 'http://127.0.0.1:8000'
$registration = @{
    full_name = 'Contact Demo'
    email = 'demo.contact@example.com'
    password = 'DemoPassword123'
    date_of_birth = '1995-05-20'
    blood_type = 'O+'
    phone = '2125550100'
} | ConvertTo-Json
$account = Invoke-RestMethod -Method Post -Uri "$api/api/auth/register/" -ContentType 'application/json' -Body $registration
$headers = @{ Authorization = "Bearer $($account.access)" }

# AC1: current contact
Invoke-RestMethod -Uri "$api/api/donors/me/contact/" -Headers $headers

# AC4: change phone, then read again
$change = @{ phone = '0123456789' } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Uri "$api/api/donors/me/contact/" -Headers $headers -ContentType 'application/json' -Body $change
Invoke-RestMethod -Uri "$api/api/donors/me/contact/" -Headers $headers

# AC2/AC3: the following are expected HTTP 400 errors; they must not save changes.
$badEmail = @{ email = 'not-an-email' } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Uri "$api/api/donors/me/contact/" -Headers $headers -ContentType 'application/json' -Body $badEmail
$badPhone = @{ phone = '123' } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Uri "$api/api/donors/me/contact/" -Headers $headers -ContentType 'application/json' -Body $badPhone
```

For AC5, create a second synthetic donor, obtain their Donor ID from their own GET,
then use the first donor's token to GET and PATCH that ID. Both must return 403,
and a subsequent GET as the second donor must show unchanged contact data.
Automated tests exercise this without manual token handling.
