# US-10: delete a donation entry or donor record

Owner: Chenshuo Li

## Scope and design

Implements the coordinator-only deletion interface from Sprint 2, based on the
Sprint 1 US-10 acceptance criteria. Uses the existing US-01 donor models and
US-04 donation models, history endpoint and eligibility calculator.

- Donation deletion physically removes only the selected entry, then returns
  updated history and eligibility calculated from the remaining entries.
- Donor deletion sets `Donor.status=deleted` and `User.is_active=False` atomically.
  It retains the donor, account, and all linked donation history. Existing access
  tokens no longer authorize requests, and sign-in is denied.
- Active and withdrawn donors can be marked deleted. Repeating donor deletion
  returns success with the same final state; deleting an already removed donation
  returns 404.
- Database operations live in `repository.py`, rules in `services.py`, and request
  handling in serializers/views. Locks use User then Donor.
- No schema migration or significant design change is required.

## API

Both endpoints require a coordinator access token and an explicit JSON body:

```json
{"confirm": true}
```

| Method | Route | Result |
| --- | --- | --- |
| DELETE | `/api/donors/<donor_id>/donations/<donation_id>/` | 200, success message, deleted ID, updated `donor` history/eligibility payload |
| DELETE | `/api/donors/<donor_id>/` | 200, success message, donor ID and `status: deleted` |

`donor_id` is the profile ID, not User.id. A donation must belong to the donor in
the URL; a mismatched pair returns 404 without deleting anything.

| Status | Meaning |
| --- | --- |
| 400 | Missing confirmation, false/null/string/numeric confirmation, non-object input, or extra fields |
| 401 | Missing/invalid token or inactive account |
| 403 | Authenticated donor attempting a coordinator operation |
| 404 | Donor or donation missing, or donation does not belong to specified donor |
| 405 | Unsupported operation, such as GET or POST on these deletion routes |

The donation response's `donor` object has the same shape as the US-04 GET
eligibility endpoint. Removing the latest donation uses the previous donation of
that type. Removing the final donation produces empty history and eligibility
today. Other donation types are unaffected. Deletion and result calculation share
a transaction; failures roll back the deletion.

## Acceptance criteria and remaining integration

| Criterion | Implementation / verification |
| --- | --- |
| AC1: delete option for coordinator | Backend permission enforced; React delete button remains frontend work |
| AC2: confirmed donation removal, eligibility update, success message | DELETE donation response; latest/older/final-entry and rollback tests |
| AC3: removed entry absent from history | Follow-up US-04 GET verified by tests |
| AC4: deleted donor absent from search/matching | Status and account changed; `repository.active_donors()` excludes removed profiles |
| AC5: history retained after donor deletion | Coordinator GET still returns the same donations and donor identity |

Search and matching endpoints are not present in this branch. Their owners must
use `repository.active_donors()` (or the same active-status/account/role filters),
then add integration tests proving removed donors are absent from the actual
search/matching responses. Do not globally filter Donor.objects: coordinator
history lookup must continue to find deleted donors.

Frontend: show deletion only to coordinators, ask for confirmation, and send the
DELETE only after confirmation. Cancellation sends no request. Render the success
message and refresh the affected history/list. Missing confirmation is rejected
by the backend even if a caller bypasses the UI.

Full story remains In progress until frontend and search/matching integration,
review, merge, and delivered-build acceptance checks are complete.

## Tests

```powershell
.\.venv\Scripts\python.exe manage.py test donors.test_deletion --verbosity 2
.\.venv\Scripts\python.exe manage.py test
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
```

The tests use synthetic records in a separate temporary database. They cover
permissions, invalid confirmation, missing/mismatched records, recalculation,
retained history, inactive accounts, repeat requests and transaction rollback.
Local validation uses SQLite; PostgreSQL locking must also be checked in CI.

## Demo script

1. Follow the README installation steps, run migrations and start the server.
2. Register a synthetic donor and use Django admin to create a synthetic active
   coordinator account (`role=coordinator`) and two whole-blood donations for the
   donor. Use dates January 1 and October 20, 2026; use valid blood type and volume.
   For another demo date, adjust dates to place one donation outside the interval
   and the other inside it. Set `recorded_by` to the coordinator.
3. Sign in as coordinator at `/api/auth/token/`; use the returned access token.
4. GET `/api/donors/<donor_id>/eligibility/` to show both donations and the current date.
5. DELETE the newer donation with `{"confirm": false}`: expect 400 and unchanged history.
6. DELETE it with `{"confirm": true}`: expect 200, success message and recalculated date.
7. GET history again: only the older donation remains.
8. DELETE the donor with `{"confirm": true}`: expect 200 and `status: deleted`.
9. GET history as coordinator: the older donation remains. Donor sign-in fails (401).
10. Demonstrate a donor token cannot delete records (403) using another active demo donor.

PowerShell request example (replace IDs and token with synthetic demo values):

```powershell
$headers = @{ Authorization = 'Bearer <coordinator-access-token>' }
Invoke-RestMethod -Method Delete -Uri 'http://127.0.0.1:8000/api/donors/<donor_id>/donations/<donation_id>/' -Headers $headers -ContentType 'application/json' -Body '{"confirm":true}'
```
