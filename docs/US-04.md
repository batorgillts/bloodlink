# US-04: check donation eligibility (backend)

Story author (Sprint 1): Chenshuo Li.

## Scope

Implements the backend for Sprint 1 US-04, using the Sprint 2 module interface
"Check eligibility" and the decision that eligibility is calculated, not stored.

A signed-in donor can read their own donation history and the next eligible date
for every configured donation type. A coordinator can read the same payload for
one donor by that donor's profile id (the shared interface also lists US-08).
Recording a donation is US-09 and is not implemented here. Until US-09 exists,
history rows are created in the admin or in tests. React is out of scope.

Registration and contact update are unchanged. The new models, view, and routes
are appended in the existing `donors` app.

## Design mapping

- Request layer: `donors/views.py` (`EligibilityView`), `donors/permissions.py`, `donors/urls.py`.
- Donor & Donation Management rules: `donors/services.py` (`get_eligibility`).
- Eligibility Calculator: `donors/calculator.py`. No Django imports. US-09 and US-18
  should call `calculate_eligibility` instead of copying the formula.
- Data access: `donors/repository.py`, `donors/models.py` (`Donation`, `DonationIntervalRule`).
- `DonationIntervalRule` is the configured rule table from the ER diagram.
  `Donation` is the donation entry from that diagram (`recorded_by`, `volume_ml`,
  `donation_type` foreign key to the rule's code).
- Next eligible date is not a column. It is the latest donation of **that type**
  plus `min_interval_days`.
- A type with no donation is eligible on the blood bank's local date
  (`America/New_York`).
- The donor is eligible when `as_of >= next_eligible_date`, so the eligible date
  itself counts as eligible (AC2).
- Identity for a donor comes from the token. `donor_id` in the URL is the Donor
  profile primary key, not `User.id`. A donor's query string cannot retarget `/me/`.

### What this version does not calculate

Sprint 2 limits eligibility to one interval per donation type. This version does
not apply cross-type deferrals (for example, 21 CFR 630.15(a)(6) deferring plasma
after a whole-blood donation) and does not apply the platelet cap of 24 collections
in 12 months from 21 CFR 640.21(e)(1). Manual deferral flags are out of scope.
Changing `min_interval_days` in the table changes the result; the numbers are not
hardcoded in the calculator.

## Configured intervals

Seeded by `donors/migrations/0003_seed_interval_rules.py`.

| donation_type | Days | Rule |
| --- | --- | --- |
| `whole_blood` | 56 | 21 CFR 630.15(a)(1)(i): one Whole Blood unit per 8 weeks |
| `red_blood_cells` | 56 | 21 CFR 630.15(a)(1)(i): one apheresis red-cell unit per 8 weeks |
| `double_red_cells` | 112 | 21 CFR 630.15(a)(1)(i): two red-cell units per 16 weeks |
| `platelets` | 7 | 21 CFR 640.21(e)(3): 7 days after a plateletpheresis of 6×10^11 or more |
| `plasma` | 28 | 21 CFR 630.3(e) and 640.32: no plasma donation in the preceding 4 weeks |

8 weeks is stored as 56 days, 16 weeks as 112, and 4 weeks as 28.

## API contract

Send `Authorization: Bearer <access token>`.

| Method | URL | Who | Behavior |
| --- | --- | --- | --- |
| GET | `/api/donors/me/eligibility/` | Signed-in active donor | Own history and eligibility |
| GET | `/api/donors/<donor_id>/eligibility/` | That donor, or a coordinator | Same payload for that profile |

Example when the donor has donated before (HTTP 200):

```json
{
  "donor_id": 1,
  "as_of": "2026-10-28",
  "no_donation_history": false,
  "message": null,
  "donations": [
    {
      "donation_id": 2,
      "donation_type": "platelets",
      "donation_date": "2026-10-25",
      "blood_type": "O+",
      "volume_ml": 200
    }
  ],
  "eligibility": [
    {
      "donation_type": "whole_blood",
      "label": "Whole Blood",
      "min_interval_days": 56,
      "last_donation_date": "2026-08-01",
      "next_eligible_date": "2026-09-26",
      "eligible": true
    }
  ]
}
```

`donations` is newest first. `eligibility` follows the seeded rule order.
August 1 plus 56 days is September 26. On October 28 that date has passed, so
`eligible` is true and the calculated date stays September 26.

No donations yet (AC4):

```json
{
  "donor_id": 1,
  "as_of": "2026-10-28",
  "no_donation_history": true,
  "message": "No previous donations are recorded.",
  "donations": [],
  "eligibility": [
    {
      "donation_type": "whole_blood",
      "label": "Whole Blood",
      "min_interval_days": 56,
      "last_donation_date": null,
      "next_eligible_date": "2026-10-28",
      "eligible": true
    }
  ]
}
```

| Status | Meaning |
| --- | --- |
| 401 | Missing or invalid token, or a deactivated account |
| 403 | Another donor's id, a withdrawn or deleted donor profile, or a coordinator calling `/me/` |
| 404 | Signed-in donor has no profile; coordinator asks for an id that does not exist |
| 405 | POST, PATCH, or DELETE |

A donor who asks for an unknown id gets 403, including when that id does not exist,
so the response does not reveal whether another donor is in the system. The 403
body does not include the other donor's history, name, email, or phone.
A coordinator asking for a missing id gets 404. Withdrawn and deleted donors can
still be read by a coordinator, because US-05 and US-10 keep donation history.

## Run and test

CI uses Python 3.12. Django 5.1 also runs on Python 3.13.

```powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py test donors.test_eligibility --verbosity 2
.\.venv\Scripts\python.exe manage.py test
```

| Acceptance criterion | Test |
| --- | --- |
| AC1: history and next date per type | `test_history_and_next_date_for_each_type` |
| AC2: eligible on the next eligible date | `test_eligible_when_today_is_the_next_eligible_date` |
| AC3: no access to another donor | `test_other_donor_is_denied_without_disclosure` |
| AC4: no history, currently eligible | `test_no_history_reports_current_eligibility` |

`test_changing_the_configured_interval_changes_the_date` shows the interval comes
from the table. `test_another_type_does_not_change_this_type` locks the per-type rule.

## Demo

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py createsuperuser
.\.venv\Scripts\python.exe manage.py runserver
```

Register a synthetic donor (same shape as US-01), then:

```powershell
$api = 'http://127.0.0.1:8000'
$registration = @{
    full_name = 'Eligibility Demo'
    email = 'demo.eligibility@example.com'
    password = 'DemoPassword123'
    date_of_birth = '1995-05-20'
    blood_type = 'O+'
    phone = '2125550100'
} | ConvertTo-Json
$account = Invoke-RestMethod -Method Post -Uri "$api/api/auth/register/" -ContentType 'application/json' -Body $registration
$headers = @{ Authorization = "Bearer $($account.access)" }
Invoke-RestMethod -Uri "$api/api/donors/me/eligibility/" -Headers $headers
```

That call is AC4: no history, and every type is eligible today.

For AC1 and AC2, sign in to `/admin/` as the superuser and add a `Donation` for
that donor. Use donation type `whole_blood`, a date 56 days before today, a valid
blood type, and a volume greater than 0. `recorded_by` is the superuser. Call the
same GET again: `whole_blood.eligible` is true and `next_eligible_date` is today.

## Handoff

- US-09 should insert `donors.models.Donation` and then reuse
  `donors.calculator.calculate_eligibility`. Do not add a second donation model.
- US-18 should treat a donor as eligible for a type when `eligible` is true
  (next date is today or earlier). A missing history means eligible.
- Frontend: GET `/api/donors/me/eligibility/` when the eligibility page opens.
  Show `message` when `no_donation_history` is true. Show `eligible` and
  `next_eligible_date` for each row.
- 401 means sign in again. 403 means this is not your record.
- The full story stays in progress until the page is connected and the change is reviewed.
