# US-05: withdraw donor registration (backend)

Story author (Sprint 1): Miaomiao Li.

## Scope

Implements the backend for Sprint 1 US-05, using the Sprint 2 module interface
"Withdraw registration" and the data-model decision to keep the donor row.

A signed-in active donor confirms withdrawal of their own account. The donor
profile status becomes `withdrawn`, and the linked user is deactivated so the
original email and password can no longer sign in. Donation rows stay attached
to that donor. React is out of scope.

This does not delete the donor (US-10) and does not add the eligible-donor
suggestion list (US-18). Coordinator search already returns only `active`
donors, which is the filter US-18 must keep using.

## Design mapping

- Request layer: `donors/views.py` (`WithdrawRegistrationView`), `donors/permissions.py`,
  `donors/serializers.py`, `donors/urls.py`.
- Donor & Donation Management rules: `donors/services.py` (`withdraw_registration`).
- Authentication & Access: `User.is_active` is set to false. Existing sign-in
  (`/api/auth/token/`) and token refresh already reject a deactivated account.
- Data access: `donors/repository.py` (`mark_withdrawn`), inside the existing
  `locked_contact` transaction. No new model, table, or migration.
- Allowed change from the ER state table: `active` → `withdrawn`.
- Identity comes from the authenticated user. `donor_id` in the URL is the Donor
  profile primary key, not `User.id`. A different id is denied whether or not it exists.
- Both writes happen in one transaction. Donation rows are not updated or deleted.

## API contract

Send `Authorization: Bearer <access token>` from registration or sign-in.

| Method | URL | Who | Behavior |
| --- | --- | --- | --- |
| POST | `/api/donors/me/withdraw/` | Signed-in active donor | Withdraw own registration |
| POST | `/api/donors/<donor_id>/withdraw/` | That same donor | Same operation for their own profile id |

Request body:

```json
{"confirm": true}
```

`confirm` must be the JSON boolean `true`. A missing body, `false`, `null`, a
non-object body, or any field other than `confirm` is rejected and nothing is saved.

Successful response (HTTP 200):

```json
{
  "donor_id": 1,
  "status": "withdrawn",
  "account_active": false,
  "donation_history_retained": true
}
```

The email and password hash are kept. Sign-in fails because the account is
inactive, not because the credentials were erased. The email stays unique, so
the same address cannot be registered again.

| Status | Meaning |
| --- | --- |
| 400 | Missing confirmation, or a field other than `confirm` |
| 401 | Missing or invalid token, or the account is already deactivated |
| 403 | Coordinator, another donor's id, an unknown id, or a profile that is not `active` |
| 404 | Signed-in donor has no Donor profile |
| 405 | GET, PATCH, or DELETE |

A 403 body does not include the other donor's name, email, or phone.
After a successful withdrawal, the access token just used, and its refresh token,
are rejected with 401. A coordinator can still `GET /api/donors/<donor_id>/` and
`GET /api/donors/<donor_id>/eligibility/` and see the previous donations.
`GET /api/donors/?email=` no longer lists that donor.

## Demo

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py runserver
```

```powershell
$api = 'http://127.0.0.1:8000'
$registration = @{
    full_name = 'Withdraw Demo'
    email = 'demo.withdraw@example.com'
    password = 'DemoPassword123'
    date_of_birth = '1995-05-20'
    blood_type = 'O+'
    phone = '2125550100'
} | ConvertTo-Json
$account = Invoke-RestMethod -Method Post -Uri "$api/api/auth/register/" -ContentType 'application/json' -Body $registration
$headers = @{ Authorization = "Bearer $($account.access)" }

# AC1
$body = @{ confirm = $true } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$api/api/donors/me/withdraw/" -Headers $headers -ContentType 'application/json' -Body $body

# AC2: expected HTTP 401
$signIn = @{ email = 'demo.withdraw@example.com'; password = 'DemoPassword123' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$api/api/auth/token/" -ContentType 'application/json' -Body $signIn
```

For AC3 and AC4, sign in as a coordinator, search `/api/donors/?email=demo.withdraw@example.com`
(empty list), then open `/api/donors/<donor_id>/` for the id returned by withdrawal.
Donation rows added before withdrawal are still on that record.

## Handoff

- Frontend: POST `/api/donors/me/withdraw/` with `{"confirm": true}` only after the donor confirms.
- 400 means confirmation was missing. 401 means sign in again. 403 means this is not your account.
- After success, drop both tokens and return to the sign-in screen. The same email will not sign in.
- US-18 must keep filtering `Donor.status = active` so a withdrawn donor is not suggested.
- The full story stays in progress until the page is connected and the change is reviewed.
